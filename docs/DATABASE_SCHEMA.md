# Database Schema

> Source of truth: [`packages/database/prisma/schema.prisma`](../packages/database/prisma/schema.prisma).
> This document explains the auth and tenancy portion of it, and what Phase 2
> adds. Rules come from [`documents/DATABASE_ARCHITECTURE.md`](../documents/DATABASE_ARCHITECTURE.md).

---

## 1. Conventions every table follows

| Rule | Why |
|---|---|
| `snake_case` columns, `camelCase` fields via `@map` | SQL convention in the DB, TS convention in code, no manual mapping |
| UUID primary keys, `gen_random_uuid()` | ids are generated by the DB, safe to expose, no sequence to leak row counts |
| `tenant_id` on every tenant-owned table | shared-schema multi-tenancy, one column that isolation depends on |
| `deleted_at` soft delete | an accidental delete is recoverable, and audit history keeps its foreign keys |
| Composite index `(tenant_id, <lookup>)` | every query filters by tenant first, so the index must lead with it |

**The one rule that carries real risk:** every query in tenant-owned tables must
filter on `tenant_id`. Postgres will not enforce it for you. A `findFirst` that
omits it reads another customer's data and no test fails. This is why route
handlers take `tenantId` from the verified session and never from a request
body, query string, or header.

## 2. Existing tables (migrated, in use)

### `organizations`, the tenant root

```prisma
model Organization {
  id        String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  tenantId  String    @map("tenant_id") @db.Uuid   // mirrors id
  name      String
  slug      String    @unique                       // globally unique, used in URLs
  createdAt DateTime  @default(now()) @map("created_at")
  updatedAt DateTime  @updatedAt      @map("updated_at")
  createdBy String?   @map("created_by") @db.Uuid
  updatedBy String?   @map("updated_by") @db.Uuid
  deletedAt DateTime? @map("deleted_at")
}
```

`tenantId` mirroring `id` looks redundant and is not. It lets every table,
including this one, carry the identical base column set, so a helper such as
`notDeleted` or a tenant-scoping utility works uniformly and there is no
special case for "the table that is the tenant".

`slug` is globally unique because it appears in URLs and in the login
disambiguation flow.

### `users`

```prisma
model User {
  id           String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  tenantId     String    @map("tenant_id") @db.Uuid
  email        String
  name         String
  passwordHash String?   @map("password_hash")   // NULL for OAuth-only accounts
  avatarUrl    String?   @map("avatar_url")
  isActive     Boolean   @default(true) @map("is_active")
  // ... base columns

  @@unique([tenantId, email])     // NOT unique on email alone
  @@index([tenantId, isActive])
}
```

Two things here decide behaviour elsewhere:

**`passwordHash` is nullable.** An account created through Google OAuth has no
password. `POST /api/auth/login` must answer 401 for it rather than crash
comparing against `null`, and "forgot password" for such an account must not
create a password out of nowhere.

**`@@unique([tenantId, email])`, not `@unique` on email.** One address can hold
accounts in two tenants, which is correct for a B2B product where a consultant
works with several clients. The cost is that login has to resolve which tenant
is meant. See section 3.2 of `AUTHENTICATION_ARCHITECTURE.md`.

### `sessions`, which is the refresh token store

```prisma
model Session {
  id               String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  tenantId         String    @map("tenant_id") @db.Uuid
  userId           String    @map("user_id")   @db.Uuid
  refreshTokenHash String    @map("refresh_token_hash")   // sha256 hex, never the raw token
  userAgent        String?   @map("user_agent")
  ip               String?
  expiresAt        DateTime  @map("expires_at")
  revokedAt        DateTime? @map("revoked_at")
  createdAt        DateTime  @default(now()) @map("created_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([tenantId, userId])
  @@index([expiresAt])
}
```

**Your prompt asked for a separate `RefreshToken` model. This table already is
it, and the merged design is better.** One row per device already carries
everything a `RefreshToken` row would, plus the `user_agent` and `ip` needed to
render a "signed-in devices" screen. Splitting them would mean a join on the
hottest path in the system to learn nothing new.

Phase 2 adds one index this design needs:

```prisma
@@index([refreshTokenHash])
```

Every refresh is a lookup by that column. Without the index it is a sequential
scan over every session on the platform, which is fine at ten users and a
production incident at ten thousand.

`onDelete: Cascade` means deleting a user drops their sessions, so a deleted
account cannot refresh its way back in.

### `audit_logs`

```prisma
model AuditLog {
  id         String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  tenantId   String   @map("tenant_id") @db.Uuid
  actorId    String?  @map("actor_id") @db.Uuid   // NULL for pre-auth events
  action     String                                // "auth.login.failed"
  resource   String                                // "user"
  resourceId String?  @map("resource_id")
  metadata   Json?                                 // ip, userAgent, reason
  createdAt  DateTime @default(now()) @map("created_at")

  @@index([tenantId, createdAt])
  @@index([tenantId, resource, resourceId])
}
```

`actorId` is nullable because the most valuable audit events happen before
anyone is authenticated: a failed login, a password reset request for an address
that does not exist. Requiring an actor would mean not logging exactly the
events an investigation needs.

**Never put a token, a password, or a reset link in `metadata`.** Audit logs are
widely readable inside an organization and are exactly where a leaked
credential would go unnoticed.

### RBAC tables

```
users ──< user_roles >── roles ──< role_permissions >── permissions
```

`Permission` is typed as a template literal in
`packages/types/src/rbac.ts`:

```ts
export type Permission = `${string}:${string}:${string}`;   // module:resource:action
```

so `'api-studio:collection:read'` type-checks and `'admin'` does not. That is
Rule 6 (never hardcode roles or permissions) enforced by the compiler rather
than by review.

Roles are per-tenant rows, not an enum, so a tenant can define a Custom role
without a migration. The five system role names live in `SYSTEM_ROLES`.

## 3. Phase 2 additions

### 3.1 `email_verifications`

```prisma
model EmailVerification {
  id        String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  tenantId  String    @map("tenant_id") @db.Uuid
  userId    String    @map("user_id") @db.Uuid
  tokenHash String    @unique @map("token_hash")   // sha256, never the raw token
  email     String                                  // the address being proven
  expiresAt DateTime  @map("expires_at")
  usedAt    DateTime? @map("used_at")
  createdAt DateTime  @default(now()) @map("created_at")

  user         User         @relation(fields: [userId], references: [id], onDelete: Cascade)
  organization Organization @relation(fields: [tenantId], references: [id])

  @@index([userId])
  @@index([expiresAt])
  @@map("email_verifications")
}
```

`email` is stored on the row rather than read from the user at redemption time.
It has to be: this table also backs *changing* an address, where the row must
remember which new address the link was issued for. Without it, a user could
request a link for `new@x.com`, edit their pending address to `boss@company.com`,
and click the original link to verify an address they never proved.

`usedAt` rather than deleting the row: a redeemed link that is clicked again
should say "already used" instead of "invalid", and the row is evidence.

### 3.2 `password_resets`

```prisma
model PasswordReset {
  id          String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  tenantId    String    @map("tenant_id") @db.Uuid
  userId      String    @map("user_id") @db.Uuid
  tokenHash   String    @unique @map("token_hash")
  expiresAt   DateTime  @map("expires_at")          // now + 1 hour
  usedAt      DateTime? @map("used_at")
  requestedIp String?   @map("requested_ip")
  createdAt   DateTime  @default(now()) @map("created_at")

  user         User         @relation(fields: [userId], references: [id], onDelete: Cascade)
  organization Organization @relation(fields: [tenantId], references: [id])

  @@index([userId])
  @@index([expiresAt])
  @@map("password_resets")
}
```

One hour, against 24 for email verification. A reset link is a full account
takeover in a single click, and it commonly sits in an inbox that may be
shared, synced to a phone, or scanned by a corporate mail filter that follows
links. Verification proves an address and grants nothing.

The token is hashed for the same reason the refresh token is: read access to
this table must not be enough to take over accounts.

**Redemption invariant.** `POST /api/auth/reset-password` runs in one
transaction: mark `usedAt`, update `users.password_hash`, reset
`failedLoginAttempts` and `lockedUntil`, then **revoke every session for that
user**. Someone resetting a password after a compromise expects the attacker to
be signed out. Leaving other sessions live makes the reset theatre.

### 3.3 Columns added to `users`

```prisma
  emailVerifiedAt     DateTime? @map("email_verified_at")
  failedLoginAttempts Int       @default(0) @map("failed_login_attempts")
  lockedUntil         DateTime? @map("locked_until")
  lastLoginAt         DateTime? @map("last_login_at")
```

All nullable or defaulted, so the migration applies to existing rows without a
backfill.

`lockedUntil` is a timestamp rather than an `isLocked` boolean so the lock
expires on its own. A boolean needs a scheduled job to clear it, and a job that
fails silently locks users out permanently.

Lockout policy: 5 failures, 15 minute lock, counter cleared on success.

### 3.4 Index added to `sessions`

```prisma
  @@index([refreshTokenHash])
```

## 4. Entity relationships

```
                    ┌──────────────────┐
                    │  organizations   │  the tenant root
                    └────────┬─────────┘
                             │ 1
        ┌────────────────────┼────────────────────┬──────────────┐
        │ n                  │ n                  │ n            │ n
   ┌────▼────┐        ┌──────▼──────┐      ┌──────▼─────┐  ┌─────▼──────┐
   │  users  │        │    roles    │      │ audit_logs │  │ permissions│
   └────┬────┘        └──────┬──────┘      └────────────┘  └─────┬──────┘
        │ 1                  │ 1                                 │ 1
        │              ┌─────▼──────────┐                        │
        │              │  user_roles    │◄───────────────────────┘
        │              │ role_permissions│    (join tables)
        │              └────────────────┘
        │
        ├──n──► sessions              refresh token per device
        ├──n──► email_verifications   NEW
        └──n──► password_resets       NEW
```

Everything hangs off `organizations`. That single fact is what makes tenant
isolation checkable: if a query touches a tenant-owned table without a
`tenant_id` predicate, it is wrong.

## 5. Migration plan for Phase 2

```bash
pnpm --filter @adysre/database exec prisma migrate dev --name auth_verification_and_lockout
```

Prisma uses `DIRECT_URL` for this, not the pooled `DATABASE_URL`. Migrations
take advisory locks and run DDL, and a transaction-mode pooler can hand
successive statements to different backends, which breaks both. See
`docs/ENVIRONMENT_SETUP.md`.

The migration is additive only: two new tables, four nullable or defaulted
columns, one index. No data is rewritten, so it is safe to apply to production
before the code that uses it ships. Deploy in that order.

Expected SQL:

```sql
CREATE TABLE "email_verifications" (...);
CREATE TABLE "password_resets" (...);
ALTER TABLE "users"
  ADD COLUMN "email_verified_at"     TIMESTAMP(3),
  ADD COLUMN "failed_login_attempts" INTEGER NOT NULL DEFAULT 0,
  ADD COLUMN "locked_until"          TIMESTAMP(3),
  ADD COLUMN "last_login_at"         TIMESTAMP(3);
CREATE INDEX "sessions_refresh_token_hash_idx" ON "sessions"("refresh_token_hash");
```

**Verify before moving on:**

```bash
pnpm --filter @adysre/database exec prisma migrate status   # "up to date"
psql "$DIRECT_URL" -c '\d users'                            # four new columns
psql "$DIRECT_URL" -c '\d sessions'                         # the new index
```

## 6. Retention

Expired rows are not self-cleaning. Sessions, verifications, and resets all
accumulate.

```sql
DELETE FROM sessions            WHERE expires_at < now() - interval '30 days';
DELETE FROM email_verifications WHERE expires_at < now() - interval '30 days';
DELETE FROM password_resets     WHERE expires_at < now() - interval '30 days';
```

Thirty days past expiry rather than at expiry, so an incident investigation can
still see the token rows involved. Wire this to a `worker` job or a Supabase
`pg_cron` schedule in Phase 6.

`audit_logs` is never deleted on this schedule. It is the compliance record.
